# 战争雷霆陆战历史决策网站
## 最终需求与验收清单 · 需求基线 v1.0

日期：2026-10-26。

**文档性质：目标状态与验收依据，不是现有代码审计或完成度报告。所有复选框均待正式实现、测试后勾选。**

依据：本对话中用户的功能要求，以及用户提供的 `format.json` 防护分析数据契约。本文不重新核验当前游戏版本、实时 BR 或历史调整表的实施状态。

标记：
- **需求**：从用户历次提示词收敛的功能要求。
- **数据约束**：用户上传格式明确规定的语义。
- **建议**：为实现可靠、可验收、低资源的产品补充的工程规则，不代表用户此前指定了该算法或数值。
- **待校准**：可以配置和解释，但不得宣称经过实战验证。

---

## 0. 产品真正要解决的问题

**在指定游戏版本、国家和陆战历史 BR 环境下，解释“版本变化会如何改变我的队列与对手”，并推荐“本国哪些 BR 和具体队列更有利”，同时尽量采用无需常驻业务后端的静态部署。**

两个核心功能：

1. **版本影响可视化**：不只列出升降权重，而是展示队列拆分、匹配边界、对手进出、防空/CAS 环境、对抗结果和推荐变化。
2. **科学匹配队列**：不只选择本国同 BR 最高分车辆，而是按逐车、逐弹药、地空联动的对抗结果，权衡对下优势、升房风险、强敌回避和队列完整性。

科技树、载具档案、换皮折叠、热力图、拆包数据和玩家技能模型是支撑系统，不是互不关联的独立演示页。

### 产品边界与默认条件

- [ ] **B01｜需求**：聚焦陆战历史模式；纳入能用于陆战队列的地面载具、固定翼飞机、直升机。航空不得混用空战历史 BR。
- [ ] **B02｜需求**：覆盖游戏国家分类和所有目标范围内载具；不能只覆盖四辆已有高精度防护数据的坦克。
- [ ] **B03｜需求**：至少保留“当前版本”和“调整后方案”；计划调整必须标记为模拟，不能冒充已经实装。
- [ ] **B04｜需求**：玩家水平初始固定为平均水平 `s=0`；保留未来技能分布与统计数据校准接口。
- [ ] **B05｜需求**：人工装填使用满级王牌条件；自动装弹机使用其对应装填机制和周期。
- [ ] **B06｜建议**：机动等性能统一声明研发/改装状态；交战距离、角度、弹药、挂载、乘员和数据版本均可追溯。
- [ ] **B07｜建议**：数据不足时继续提供科技树和可用的粗粒度分析，但显式显示缺项、估计层级和不确定性；覆盖全目录不等于所有载具都有同等精度。

## 1. 核心功能一：可视化版本变化带来的影响

### 1.1 比较对象与一致性

- [ ] **V01｜需求**：用户能切换当前/调整后版本，并在相同国家、目标 BR、队列与交战条件下比较。
- [ ] **V02｜需求**：科技树卡片清楚展示旧 BR、新 BR 和升降标记；可筛选受影响载具。
- [ ] **V03｜需求**：展示火力、防护、机动、辅助设备、雷达或挂载变化，不把版本变化仅限于 BR。
- [ ] **V04｜建议**：比较两版时固定评分算法和参数；算法升级需要单独标记，避免把算法差异误报成游戏平衡调整。
- [ ] **V05｜建议**：调整表旧值与基线冲突、载具无法匹配、重复行及只有文字说明的变化都有审计记录，不能静默覆盖或随意替换载具。

### 1.2 环境与队列影响

- [ ] **V06｜需求**：对每个国家和每个有效 BR 重新计算两版环境，而不是只检查少数关注载具。
- [ ] **V07｜需求**：展示对手进入/离开主力匹配范围、威胁等级变化、强敌避让边界变化。
- [ ] **V08｜建议**：敌我双方均使用同一目标版本数据重算；不能用新版本己方搭配旧版本敌方。
- [ ] **V09｜需求**：识别地面与航空不同步上调、关键防空或主战离开原档位、整队最高 BR 上移等“队列拆分”情况。
- [ ] **V10｜建议**：拆分公告表示原组合的匹配成本或协同发生变化，不声称载具从此不能同时编队。
- [ ] **V11｜需求**：生成新版环境公告：发生了什么、受影响国家/BR、相关车辆、推荐采取何种替换或升档方案。
- [ ] **V12｜需求**：可视化 CAS 攻击窗口和敌方防空覆盖变化；敌方坦克的机动、防护与航空压制需要联动分析。
- [ ] **V13｜建议**：分别展示“旧队列原成员带到新版”与“新版重新优化的队列”，不能只替换推荐后隐藏原队列的损失。
- [ ] **V14｜需求**：展示各国推荐 BR、推荐队列和解释指标在版本间的变化；重大变化可定位到对手和具体对抗。
- [ ] **V15｜建议**：公告和对比均能点击回到科技树、对应队列或矩阵；不能成为孤立的新闻文本。

### 1.3 推荐的展示组成

**建议**：版本概览、全国/BR 影响图、科技树变更标记、队列拆分公告、固定队列前后对比、新旧推荐对比、敌方进入/离开列表。具体视觉样式可变，但上述信息必须能被用户找到。

## 2. 核心功能二：科学匹配队列系统

### 2.1 搜索与合法编队

- [ ] **Q01｜需求**：遍历各国全部有效 BR 上限，分别产出当前版和调整版推荐，不能仅推荐用户当前选择的一档。
- [ ] **Q02｜需求**：每个候选由真实可编队载具组成，使用正确的陆战历史 BR；整队匹配依据实际成员计算。
- [ ] **Q03｜建议**：候选 BR 上限大于实际队列最高 BR 时，以实际最高 BR 分析；不得凭空把低档队列按高档评价。
- [ ] **Q04｜建议**：提供槽位数、常规研发/特种载具及可用载具约束；推荐不能无说明地依赖用户不可用的载具。
- [ ] **Q05｜需求**：综合主战、侧翼/侦察、防空、航空等任务价值，而不是对单车总分排序后截取前几辆。
- [ ] **Q06｜建议**：允许导入或手工修改队列，并用同一模型与自动推荐比较；自动推荐可一键采用。
- [ ] **Q07｜建议**：搜索方法与范围可解释；遍历全部 BR 不等于穷举全部载具组合，采用剪枝或启发式时不得宣称保证全局最优。

### 2.2 评价目标

- [ ] **Q08｜需求**：逐一计算每辆己方载具对每辆相关敌方载具的表现，并保留具体弹药、挂载和交战条件。
- [ ] **Q09｜需求**：衡量对下优势、同档表现和升房后的风险；推荐目标是有利环境下的综合收益，而不只是峰值火力。
- [ ] **Q10｜需求**：识别版本强势对手与危险档位，显示候选队列能避开的对象和避不开时的应对能力。
- [ ] **Q11｜建议**：区分规则上的“不能进入该匹配区间”与模型上的“预计威胁较低”；没有排队统计时不声称能提高降房概率。
- [ ] **Q12｜需求**：考虑地空协同、对方防空、己方航空挂载质量和数量；不能因地面总分接近就忽略航空优势。
- [ ] **Q13｜需求**：防空对防空的直接交战在整队汇总中降权，同时保留单次交战原始分析。
- [ ] **Q14｜建议**：防空降权不等于防空角色不重要；防空对敌机的任务价值、对常规地面目标的实际能力仍应单独计算。
- [ ] **Q15｜建议**：将航空出击成本和获得重生点的条件纳入可用性，避免把空中火力视为随时免费可用。
- [ ] **Q16｜建议**：未知对手出现率和升降房比例使用明确标注的先验；后续统计可以替换，不能把“所有载具等概率”写成实测事实。
- [ ] **Q17｜建议**：呈现平均表现与不利情景风险，避免只挑最有利视角或最弱对手支撑推荐。

### 2.3 推荐输出

- [ ] **Q18｜需求**：每国输出推荐 BR、具体队列、主要弹药、航空合法混挂和各载具任务定位。
- [ ] **Q19｜建议**：至少展示最佳候选及可比较的备选；说明哪个适合稳健发挥、哪个依赖航空或特定打法。
- [ ] **Q20｜需求**：每个推荐有可展开依据：优势对手、危险对手、强敌回避、地空组合与版本影响。
- [ ] **Q21｜建议**：标注分数方向、模型版本、资料覆盖率、缺失输入与敏感条件；分数不冒充游戏胜率或保证收益。

## 3. 载具档案与逐车对抗矩阵

### 3.1 四个基础维度

| 维度 | 最终需要展示和参与分析的字段 |
|---|---|
| 机动 | 前进极速、后退极速、功重比、中心转向；统一性能状态。 |
| 火力 | 具体主力弹药及距离/角度条件下的穿深；人工满级王牌装填或自动装弹周期；俯仰角、方向机速度、高低机速度。 |
| 防护 | 首上、首下、侧面、弱点区域的防护；区分动能、化学能、ERA、复合装甲、防崩落内衬与具体弹药响应。 |
| 辅助 | 大于等于 12.7 mm 的高射/同轴重机枪；抛射烟、引擎烟；夜视与热像，区分代数和使用位置。 |

- [ ] **C01｜需求**：上述字段形成可查看的载具档案及分析，不只保留一个无法解释的总分。
- [ ] **C02｜建议**：装甲物理厚度、RHAe、模型中间量和穿透概率分开显示；未知等效厚度不能由无校准中间量补成真实值。
- [ ] **C03｜需求**：M1A2 + M829A2 与 HSTV-L + XM885 对同一目标的结果分别计算；不能按国家、BR、炮口径或 KE 大类共用结果。
- [ ] **C04｜建议**：正反两个攻击方向各自计算；缺反向数据时不能用 `1 - 正向分数` 伪造对手表现。
- [ ] **C05｜建议**：对抗条件包括版本、攻击者/目标构型、弹药、射距、观察/入射姿态、技能及相关设备；缺失条件可见。
- [ ] **C06｜建议**：机动、炮控、观瞄、装填影响发现、先手、落点、暴露和后续射击；避免同一属性在多个模块中重复无约束加分。
- [ ] **C07｜建议**：持续交战考虑瞄准与装填可重叠、受损、首轮未达成目标等情景；不能把期望穿透值直接当作每发击毁概率。

### 3.2 防空与航空

- [ ] **A01｜需求**：防空包括导弹射程、过载、架上即用弹数、雷达扫描角及周期、机炮投射量。
- [ ] **A02｜建议**：区分架上弹与总携弹、搜索与跟踪、不同扫描模式和视线限制；多车系统不能被重复当成若干独立满功能槽位。
- [ ] **A03｜需求**：航空按武器型号、数量和质量评价；AGM-65D 与 Kh-38MT 不得仅因都为红外制导而等分。
- [ ] **A04｜建议**：区分飞行包线、导引头能力和实际可用攻击条件；最大射程不等于任意条件下可靠命中距离。
- [ ] **A05｜需求**：分析实际可同时携带的混合挂载，不把不同互斥预设的最大数量相加。
- [ ] **A06｜建议**：核验挂点、载重、冲突和依赖；反辐射弹的作用依赖目标雷达与辐射条件，不能按通用对地导弹无条件计数。

## 4. 防护概率数据与玩家模型

### 4.1 保持上传数据的真实语义

依据：用户提供的 `format.json`。

- [ ] **H01｜数据约束**：正确读取 `penetration_probability`、`status`、`material_response_flags`；输入是按角度排列的像素概率数据。
- [ ] **H02｜数据约束**：`model_required_charge_mm` 是模型装甲栈中间消耗量，不是 RHAe；不得把它作为等效防护厚度发布。
- [ ] **H03｜数据约束**：保留 `status=0` 背景、`1` 射线上无受保护内部目标、`2` 未知几何/材料、`3` 有条件估计；NaN 不当作零。
- [ ] **H04｜建议**：状态 1 不能被宣传为车体不可受损或必定未击穿；它只约束当前数据的保护目标指标。
- [ ] **H05｜数据约束**：角度顺序、像素方向、真实采样间距及图像尺寸来自元数据；HD 放大图没有新增射线样本。
- [ ] **H06｜建议**：不把示例 24 个角度、434×137 网格和 25 mm 间距写死在通用接口里；对未来不同形状进行校验。
- [ ] **H07｜数据约束**：保留射线 `ray_id` 与角度/像素的索引关系；材料通过对应 `.layers.json` 的 `node` 索引查找；无出口 `+Inf` 不当正常厚度。
- [ ] **H08｜建议**：用目标构型、精确弹药、物理射距/参数、姿态、几何版本、配置版本和模型版本建立缓存键；参考弹的热力图不能变成其他车辆拥有该弹的证据。
- [ ] **H09｜建议**：无对应热力图时显示缺失，或显式回退到独立标注的粗模型；不能复用相近弹种而仍标“精确计算”。
- [ ] **H10｜数据约束**：结果标为分层直线路径模型的条件估计，不能称作已校准的游戏穿透率、击毁率或胜率。

### 4.2 默认玩家水平与非均匀瞄准

- [ ] **S01｜需求**：默认 `s=0`，不依赖玩家登录、个人战绩或 StatShark 在线可用性。
- [ ] **S02｜需求**：保留技能为连续变量和正态潜变量的接口；正态分布只是暂定假设，不声称已由统计数据证实。
- [ ] **S03｜需求**：瞄点不均匀：有一般中心瞄准，也有朝向可穿区域稳健中心的偏好，随技能调整。
- [ ] **S04｜建议**：区分“选择瞄点”和“实际落点误差”；落点允许落到厚甲、未知区域及目标外，不能截断到可击穿区后归一化。
- [ ] **S05｜建议**：瞄点中心必须落在目标区域内；连通域质心落在空洞或区域外时改用有效的稳健点。
- [ ] **S06｜需求**：瞄准误差受技能、距离、目标/自身运动和炮控条件影响；需要支持不同方向的误差。
- [ ] **S07｜需求**：高水平更能利用弱点、机动、灵活性和射速；低水平更依赖单发效果和容错防护。将其作为可校准行为倾向，不硬写所有车都必然遵循的结论。
- [ ] **S08｜建议**：单发效用为实际落点分布与条件穿透图的积分；未知区域计入不确定性或上下界，不能通过只保留有效像素抬高得分。
- [ ] **S09｜建议**：仅改变瞄准距离时，清楚说明没有重新计算弹药物理穿深；需要新射距物理结果时必须取对应缓存或重新离线计算。
- [ ] **S10｜需求**：保留用战绩大数据/StatShark 统计调整技能先验和参数的接口；统计不可取得时默认模型仍能运行。

## 5. 科技树、威胁展示与换皮关系

- [ ] **T01｜需求**：按国家复刻科技树的等级、分支、文件夹与前置关系；覆盖地面和陆战可用航空。
- [ ] **T02｜需求**：选择国家、BR 和版本后，联动展示可组队载具、推荐队列、对手与威胁类别。
- [ ] **T03｜建议**：区分主力匹配 BR 区间和高 BR 队列携带的更低 BR 载具；“移出主力区间”不能自动写成“绝不遇见”。
- [ ] **T04｜需求**：威胁区支持换皮折叠，展开后保留每个成员的国家、BR、弹药、构型差异和评分。
- [ ] **T05｜需求**：BMPT-72 与普通 T-72B 不作为同一无差别换皮合并；ERA、内衬、武器差异独立保留。
- [ ] **T06｜需求**：Leopard 2A4/A5/A6/A7 分开评价与展示；底层仍可记录车族血缘关系，但不以车族替代战斗构型。
- [ ] **T07｜建议**：只把确认关键配置一致的成员标为“换皮”；同底盘、同车族、同材料名都不足以判定等价。
- [ ] **T08｜建议**：折叠是显示操作，不改变配对得分或样本权重；不能因同车有多个国家换皮就无依据地增加出现概率。
- [ ] **T09｜建议**：查看具体敌人时能展开己方每辆车的结果和数据来源；矩阵、热力图、档案与推荐使用同一全局版本状态。

## 6. 数据源、版本与更新

- [ ] **D01｜需求**：官方 Wiki 用于当前载具目录、名称、科技树、陆战历史 BR 与可读属性。
- [ ] **D02｜需求**：腾讯调整表作为调整方案来源，保留原始行和载具映射，不能把计划直接并入当前版。
- [ ] **D03｜需求**：Datamine 用于车辆配置、武器、材料、雷达、挂载及其他可核验底层参数；客户端几何用于防护构建。
- [ ] **D04｜建议**：每条关键数据保存来源、采集时间、游戏版本/提交、转换方法与可信状态；不能把不同快照拼成无说明的“当前”。
- [ ] **D05｜建议**：名称使用稳定载具 ID 和弹药 ID 关联；本地化名、别名与历史改名不改变实体身份。
- [ ] **D06｜建议**：处理配置继承、改装状态和字段单位；读取到字段不等于已确定它在玩家物理模型中的意义。
- [ ] **D07｜建议**：提供缺项、冲突、未映射车辆与版本不一致的可审计清单；不静默用零补齐。
- [ ] **D08｜建议**：当前版和方案版共用版本化模型配置；数据更新可增量构建、复现与回滚。
- [ ] **D09｜建议**：StatShark 或其他统计作为离线校准/验证输入，记录模式、时间窗、样本与偏差；不把载具胜率直接当作纯性能，也不凭总体 K/D 直接推导厘米级瞄准误差。

## 7. 尽可能降低托管资源的实现方案【建议】

### 推荐架构

```text
Wiki / 调整表 / Datamine / 本地 GRP / 防护 NPZ / 可选统计
                             ↓
                  本地或构建任务：采集和校验
                             ↓
            几何与防护预处理、有限配对、队列搜索、版本差分
                             ↓
              版本化静态文件：HTML/CSS/JS/压缩数据
                             ↓
               静态 HTTP 托管（可选 CDN 缓存）
                             ↓
             浏览器：展示、筛选、按需小规模重算
```

- [ ] **L01｜建议**：公开查询与两个核心功能不依赖常驻业务后端、数据库、GPU 服务、登录系统或服务端渲染。
- [ ] **L02｜建议**：抓取、GRP 解码、射线计算、全国 BR 扫描和公告生成在本地/构建阶段完成，而非用户访问时启动。
- [ ] **L03｜建议**：在线仅发布精简摘要、推荐结果、受匹配条件约束的对抗数据和按需热力图；不把全部 GRP、解压文件和射线层缓存装入首页。
- [ ] **L04｜建议**：按版本/国家/BR/载具/弹药分片；先加载默认版本和当前视图，详情点击后再下载。
- [ ] **L05｜建议**：图片和可视化按需加载；全量原始数据单独归档，四车研究查看器不成为主站启动的必要依赖。
- [ ] **L06｜建议**：避免物化“所有车辆×所有弹药×所有距离×所有角度×所有技能×所有版本”的稠密笛卡尔积；只构建真实可用弹药和相关匹配配对，并复用相同物理数据。
- [ ] **L07｜建议**：仅 BR 变化时复用几何与防护图，重算环境与队列；武器、防护或模型变化才失效相关缓存。
- [ ] **L08｜建议**：前端自定义队列只组合小型缓存或在 Web Worker 中局部计算；大计算不能阻塞主线程。
- [ ] **L09｜建议**：偏好和自选队列默认保存在浏览器本地；避免为不需要的云同步引入账号和数据库。
- [ ] **L10｜建议**：使用内容哈希缓存、压缩和有限本地缓存；量化概率要测误差，必须保留未知和真实零概率的区别。
- [ ] **L11｜建议**：提供完整静态部署包与可复现构建说明；基础功能可由普通静态 HTTP 服务运行，不要求第三方接口实时响应。
- [ ] **L12｜建议**：优先静态目录部署；可选单文件离线导出不得迫使正式站点打包全部国家、版本和热力图。
- [ ] **L13｜建议**：记录首屏传输量、数据请求量、浏览器峰值内存、交互耗时、总存储、构建耗时和增量更新量，不只衡量服务器 CPU。
- [ ] **L14｜建议**：静态数据与构建凭据分离；发布物中不含访问令牌或本地敏感配置。

### 初始资源验收预算【建议，待用实际构建测量后定稿】

| 指标 | 建议目标 | 口径 |
|---|---:|---|
| 业务服务器进程 | 0 个 | 不含静态文件/CDN 基础服务本身 |
| 在线数据库/GPU | 0 | 核心查询、版本比较与预计算推荐不依赖它们 |
| 核心 HTML/CSS/JS | 压缩后不超过 1 MB | 不含按需数据、图片和热力图 |
| 默认视图首屏数据 | 压缩后不超过 2 MB | 不含用户主动展开的图像/热力图 |
| 首次进入加载全量大文件 | 0 个 | 不自动载入 GRP、原始 NPZ 或全部视角图 |
| 缓存命中的筛选响应 | 目标 200 ms 内 | 需固定测试设备、浏览器与数据规模；不是已测结果 |

这些是建议预算，不是用户已经确认的硬指标，也不是现有页面已达标的声明。具体服务商和价格不在本需求基线内。

## 8. 关键端到端验收案例【建议】

表中 BR 数值是历史示例/测试夹具，不是对当前实装值的断言。实际生产数据来自固定快照。

| 编号 | 场景 | 必须观察到的结果 |
|---|---|---|
| AT01 | 测试夹具：以色列地面与 Ayit 原为 10.0，方案中地面 10.3、航空 10.7 | 公告说明组合最高 BR 变为 10.7；展示维持全组合与移除/替换航空的差别，并重新给出候选。 |
| AT02 | 使用按最高 BR、最大跨度 1.0 的测试规则；己方 10.7，敌方分别为 11.7 与 12.0 | 11.7 位于上界，12.0 在外；双方按同版数据判断，不能只记住“飞机上调就遇到 BMPT”。 |
| AT03 | 只调整敌方 BR，己方数据不变 | 环境图、威胁清单、推荐依据随之更新，而不是仅看己方变更。 |
| AT04 | 对同一 T-90M 测试 M1A2/M829A2 和 HSTV-L/XM885 | 两个独立配对；只有 M829A2 图时，不能把它套给 XM885。 |
| AT05 | 折叠换皮与拆分构型 | 普通等价换皮可折叠，BMPT-72/T-72B、豹 2 A4/A5/A6/A7不丢失差异；折叠前后矩阵汇总不变。 |
| AT06 | 查看防空—防空与防空—航空交战 | 前者在整队评价中降权；后者仍作为关键任务评价，不被一起削弱。 |
| AT07 | 空中预设含反辐射弹或互斥挂载 | 只计合法同时挂载；不满足反辐射条件时不把该弹计为无条件通用对地战果。 |
| AT08 | 热力图存在未知、NaN、背景和无内部目标 | 分类与图例保留，未知不会变零；结果有覆盖率/区间，落空概率不被截断消失。 |
| AT09 | 默认技能与以后调整技能 | 默认 s=0 可运行；改变技能影响瞄点/误差而不是修改装甲物理概率；所有行为参数标未校准。 |
| AT10 | 仅更改瞄准距离而没有新弹道图 | 页面说明只改变瞄准误差，没有伪造对应距离穿深结果。 |
| AT11 | 对比固定旧队列和新版本优化队列 | 分别解释版本损失与重新编队收益，算法口径一致。 |
| AT12 | 无业务 API、数据库、GPU，使用普通静态 HTTP 服务 | 两个核心功能、科技树、缓存矩阵和按需热力图均可运行；首次加载不下载全部原始数据。 |
| AT13 | 固定输入快照、模型参数与种子重复构建 | 结果可复现；构建报告可定位来源、未知项和缓存失效原因。 |

## 9. 不应冻结成硬性产品规则的内容

| 项目 | 正确处理 |
|---|---|
| 历史示例中的 10.0、10.3、10.7、11.7 等 BR | 作为版本数据或测试夹具，不写死成永久规则。 |
| 防空互打系数 0.10、其它配对系数 | “降低防空互打贡献”是需求；具体数值是待校准配置。 |
| 此前的固定评分比例，例如 25/25/20/10/10/10 | 不是用户已确认的评分标准；需要统一口径、测试和敏感性分析。 |
| 高中低技能的固定四维权重 | 作为可检验假设，不把未经验证的线性权重称作科学结果。 |
| 正态技能分布、落点高斯方差、Softmax 温度 | 初始模型假设；默认 s=0，保留后续拟合接口。 |
| 对手频率与升降房比例 | 缺数据时显式先验；不能杜撰实测分布。 |
| 最大雷达/导弹范围 | 配置与条件输入，不是实战保证锁定、保证命中范围。 |
| 防护概率或模型厚度 | 条件估计/中间量，不是已校准胜率、击毁率或 RHAe。 |
| 某车型“强势” | 应有版本、情景与证据，支持关注名单，但不能作为永久特权加分。 |

## 10. 暂不属于首个正式版本的必需功能

以下内容不应阻碍两项核心功能交付：账号与云端收藏、实时 StatShark 抓取、服务器端实时几何解码、全车 3D 渲染、所有距离/姿态/技能组合的在线物理仿真、自动操作游戏、保证降房或保证胜率。

必须保留扩展接口，但不必预先为这些扩展支付持续托管成本。

## 11. 最终完成定义

- [ ] **F01｜核心一完成**：用户能从任意选定国家/BR/旧队列看到版本变化如何影响队列最高 BR、相关对手、防空/CAS 环境和推荐，并定位重大变化原因。
- [ ] **F02｜核心二完成**：用户能为每个国家得到经过全 BR 扫描、合法约束、逐车对抗和地空协同评价的推荐队列及备选，查看优势、风险与未知，而不是只有不透明总分。
- [ ] **F03｜可信度完成**：来源、版本、参数、缺失项和模型边界可见；没有把粗模型冒充精确物理或把条件概率冒充游戏胜率。
- [ ] **F04｜资源目标完成**：不启用常驻业务后端、数据库和在线 GPU，两个核心功能仍能运行；原始大数据、重计算与在线访问分离。
- [ ] **F05｜交付完成**：交付静态站点、源代码、构建/增量更新脚本、数据契约、模型配置、变更审计、自动测试、端到端验收与资源测量报告。

**最终产品不是一张漂亮的装甲图，也不是一个泛化“战力排行榜”，而是一个能解释版本变化、能依据具体对抗推荐队列、且能低成本静态托管的陆战历史决策工具。**
